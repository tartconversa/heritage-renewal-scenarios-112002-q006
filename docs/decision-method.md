# 决策方法与价值判断边界

本文件说明 `renewal_analytics` 如何把工程投入、居民可达性、保护要求与运营能力
放进同一份可比较资料，以及哪些边界不允许被算法抹平。

## 1. 两层裁决：硬约束与价值偏好

资料中的方案结论分为两个不可混淆的层次：

1. **不可行（硬约束冲突）**：方案工程类型超出建筑 `permitted_work`、目标建筑
   无许可依据或引用不存在。不可行是一票否决：方案不进入任何加权评分与排序，
   其保护约束**不能被可达性、受益人数、低成本等高分指标折算抵消**。
2. **可行但价值偏好不同**：通过保护审查的方案之间，差异体现在收益构成
   （服务了哪些群体、节省多少通行时间）、成本区间与运营状态上。分析层只并列
   这些结构，不指定哪个群体更重要——那是居民与决策者的政治选择。

## 2. 未知不是零，区间不是点估计

- 所有空单元格解析为 `None`（未知），在报告中显示“未知”，与数值 0 严格区分。
- 成本始终以 `estimate_low ~ estimate_high` 区间呈现与加总；区间一侧缺失时，
  合计区间只覆盖已知侧并标注不完整，绝不补零。
- 通行节省量任一侧耗时缺失时保持未知，不进入加权聚合。

## 3. 稳定容量的认定规则

服务容量只有同时满足“有运营责任方”与“启用日期已确认（且容量非空）”时才计为
稳定容量（`stable`）。其余状态分层展示：

| 状态 | 含义 | 能否计入稳定容量 |
| --- | --- | --- |
| `stable` | 责任方、容量、启用日期齐全 | 是 |
| `unconfirmed` | 有责任方但启用日期或容量缺失 | 否，仅列未确认 |
| `uncommitted` | 指定运营方无该服务承诺 | 否 |
| `no_operator` | 方案未指定运营责任方 | 否 |

“设施建成”不等于“可持续服务”。服务覆盖视图还会暴露错配：街巷把居民引向
没有运营承诺的服务，或有容量承诺却没有任何可达改善。

## 4. 组合方案与共享街巷的去重

- 街巷通行改善可能同时服务多个片区与群体，可达记录按 `(service_id, group_code)`
  合并：施工前取最差现状、施工后取最优值，同一键只计一次节省。
- 容量按 `(operator_id, service_id)` 去重，同一承诺不重复计入。
- 成本区间逐项相加；组合中任一成员不可行，则整个组合不可行。
- 组合枚举默认最多 3 个成员，截断会在报告中显式声明。

## 5. 权重外生与加权分的可用性

权重只能通过独立 CSV 提供，列为
`group_code, weight, source, representativeness`（示例见 `examples/weights.csv`）。

- **不提供权重文件**：只输出分群体节省矩阵，不生成加权总分。
- **权重未覆盖全部受影响群体**，或某群体节省量未知：聚合分标记为不可用，
  并说明缺失方；不得用部分群体的分数宣称总体最优。
- **权重完整时**：给出加权聚合分，但同时原样附出来源与代表性说明，明确它是
  价值判断的量化，不是客观共识。
- 不可行方案在任何情况下都不参与加权。

## 6. 版本留痕与意见时效

- 每次评估对四张输入表计算 SHA-256 组合哈希（快照），报告与 JSON 结果都绑定
  该哈希；历史快照保存在 `reports/snapshots/`。
- 评估意见以 JSON Lines 追加存储（`reports/opinions.jsonl`），不提供修改/删除。
- 输入修订后重新评估会产生新快照；读取旧意见时若哈希不一致，标注
  `stale=true`（依据已过期，需复核），意见正文与原哈希原样保留。
- 施工范围变化会同时改变可达性、受影响群体与保护审查结论，因此任何输入文件
  变化都要求整体重评，而不是在旧结论上做局部修补。

## 7. 需求追溯链

报告第 9 节为每条 `(群体 × 服务)` 需求建立链条：相关方案 → 施工前后耗时与
最优方案 → 各方案工程成本区间 → 目标建筑保护等级与许可边界 → 该服务的运营
容量状态。任一环节缺失都保留显式备注，使决策者能追查一项居民需求如何影响
设施规模、保护边界与运营成本，而不是只看到一个汇总分。
